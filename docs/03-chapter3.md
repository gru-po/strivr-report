# Capítulo III: Requirements Specification

En este capítulo se especifican los requisitos del producto digital **Strivr** a partir del análisis realizado en el Capítulo II. La especificación se organiza en tres secciones: el conjunto de Epics y User Stories con sus Acceptance Criteria, el Impact Mapping que vincula los Business Goals con los entregables del producto, y el Product Backlog con la estimación y priorización de cada User Story.
I'll start by reading both reference files.
## 3.1. User Stories

El conjunto de requisitos se estructuró en diez Epics que agrupan las capacidades del producto: los siete plugins funcionales del dominio (IAM, Profiles & Stats, XP & Leveling, Quests, Duels, Skill Sets & Badges, Forums, Leaderboards & Notifications), el sitio web estático (Landing Page) y las capacidades del RESTful API expresadas como Technical Stories con el rol *Developer*.

Los Acceptance Criteria se redactan en tercera persona y tiempo presente, sin referencias a detalles de interfaz de usuario, siguiendo la estructura Gherkin (Given–When–Then). La cláusula **Dado que** describe únicamente el estado previo del actor o del sistema; la cláusula **Cuando** describe la acción que ejecuta el actor de la User Story y constituye el único disparador del escenario; la cláusula **Entonces** describe exclusivamente la respuesta observable del sistema. Los únicos escenarios cuya cláusula **Cuando** corresponde a un disparador no ejecutado por una persona son los de las funcionalidades desatendidas —la resolución automática de duelos al cierre del periodo de votación (US22) y la propagación de eventos del bus del core (TS06, TS07)—, en las que el disparador es el vencimiento de un plazo o la publicación de un evento de dominio. Las excepciones a la estructura Gherkin corresponden a reglas de negocio o restricciones que no dependen de condiciones.
